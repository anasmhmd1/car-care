# منظومة بريق للعناية المتنقلة بالسيارات

بريق تطبيق عربي أحادي البراند يجمع الموقع العام، حجز العميل، التشغيل الميداني، ولوحات الإدارة في مشروع Next.js واحد. التقنية الحالية: Next.js 15.5 وReact 19 وTypeScript وPrisma 6 وPostgreSQL 16.

الدفع في النسخة الحالية يدوي عبر رفع إثبات التحويل ومراجعته؛ لا توجد بوابة دفع أو رسائل آلية أو خرائط خارجية.

## ما هو منفذ

- كتالوج عام للخدمات والباقات ومناطق التغطية وصفحات السياسات وSEO.
- حساب عميل لإدارة السيارات والعناوين والحجوزات وإثباتات الدفع وطلبات الإلغاء/التأجيل والشكاوى، واستخدام رصيد التعويضات بسجل تدقيق، وطلب الاشتراكات ورفع إثباتاتها ومتابعة تاريخ مراجعتها، وإرسال طلب استعادة كلمة مرور يدوي.
- لوحة المالك، وإدارة الكتالوج في `/admin/catalog` بما فيها سياسات إلغاء قابلة لإعادة الاستخدام والإصدار ومرتبطة بكل خدمة، وإعداد التشغيل في `/admin/setup`، والتقويم في `/admin/calendar`، والتقارير وتصدير CSV في `/admin/reports`، واعتماد صور المعرض في `/admin/gallery`، وإعادة حجز نهائي إلى المراجعة الإدارية بسبب مسجل دون عكس صامت للتسوية أو الـHolds أو التوزيع أو سجل زيارات الاشتراك.
- لوحة تشغيل لمراجعة الدفع وقبول الحجز والتوزيع والتحصيل والاسترداد والجودة والشكاوى وإثباتات دفع الاشتراكات وتفعيلها وطابور استعادة كلمة المرور اليدوي، مع وصول مقيد بعضوية الفرع والصلاحية إلى الفرق والدوام والإجازات، وسجل الفرع في `/operations/audit`، والتقويم، والتقارير/CSV، وإدارة اشتراكات العملاء، وشاشة `/operations/pricing` المفوضة لتعديل الأسعار فقط مع Audit. يدير Operations Manager الفرق والإتاحة افتراضيًا تحت `workforce.manage`، أما إنشاء حساب Employee أو تعديله أو تعطيله فيحتاج Grant اختياريًا من `employee.manage`. وتسمح `booking.override_close` المستقلة بإغلاق استثنائي مسبب ومدقق من مرحلة الخدمة/الجودة مع إبقاء شرط الفريق وصفر المبلغ المستحق وسجل الاشتراك.
- شاشة موظف ميداني لتنفيذ الحالات والـChecklists ورفع صور قبل/أثناء/بعد الخدمة. يظهر `/staff/delegated` فقط عند وجود Grant صريح ومحدد النطاق لإحدى الصلاحيات الاختيارية السبع: مراجعة الدفع، قبول الحجز، رؤية غير المسند، اعتماد الجودة، تسجيل التحصيل، تسجيل إثبات الاسترداد دون اعتماده، أو الإغلاق النهائي.
- لوحة System Admin لإنشاء حسابات الملاك، وضبط حد الفروع، ومراجعة طلبات الفروع وإنشائها، وإدارة حالة المستخدم/الفرع والإعدادات وسجل التدقيق.

## المتطلبات

- Node.js 20 أو أحدث.
- npm 10 أو أحدث موصى به مع `package-lock.json` الحالي.
- PostgreSQL 16 مع صلاحية تفعيل `pgcrypto` و`btree_gist`، أو Docker وDocker Compose v2.

## التشغيل المحلي

ثبّت الاعتمادات:

```bash
npm ci
```

انسخ ملف البيئة. لا ترفع `.env` إلى Git.

Linux/macOS:

```bash
cp .env.example .env
openssl rand -base64 48
```

Windows PowerShell:

```powershell
Copy-Item .env.example .env
$bytes = New-Object byte[] 48
[Security.Cryptography.RandomNumberGenerator]::Fill($bytes)
[Convert]::ToBase64String($bytes)
```

ضع الناتج في `SESSION_SECRET` (32 حرفًا على الأقل). التطبيق لا يقرأ `JWT_SECRET`. اضبط `DATABASE_URL` لاتصال التطبيق و`DIRECT_URL` لاتصال PostgreSQL مباشر قادر على تشغيل الهجرات؛ يجوز أن يتساويا محليًا.

طبّق الهجرات ثم شغّل التطبيق:

```bash
npm run db:generate
npm run db:migrate:deploy
npm run db:migrate:status
npm run dev
```

افتح `http://localhost:3000`. لا تستخدم `prisma db push` في النشر.

## Seed تجريبي آمن

الـSeed مخصص للتطوير أو قاعدة اختبار قابلة للمسح. ينشئ بيانات Sample قابلة للتعديل: الأدوار الخمسة، فرعًا، مناطق وفرقًا وساعات عمل، سبع خدمات، إضافات، Checklists، باقات، عملاء، وحجوزات في حالات مختلفة. كما يكتب ملفات إثبات تجريبية خاصة وثابتة تحت `UPLOAD_DIR`؛ لذلك تحتاج اختبارات القبول إلى قاعدة البيانات ومسار تخزين قابل للكتابة.

التنفيذ deterministic وقابل للإعادة دون مضاعفة سجلاته الثابتة. يرفض العمل عندما تكون `NODE_ENV=production`، ولا يعمل دون متغيري كلمة المرور، ولا يطبعهما، ويُلزم جميع الحسابات التجريبية بتغيير كلمة المرور عند أول دخول.

Linux/macOS:

```bash
export SEED_PASSWORD="$(openssl rand -base64 24)"
export SEED_ADMIN_PASSWORD="$(openssl rand -base64 32)"
npm run db:seed
```

Windows PowerShell:

```powershell
$env:SEED_PASSWORD = "temporary-value-at-least-12-characters"
$env:SEED_ADMIN_PASSWORD = "different-value-at-least-16-characters"
npm run db:seed
Remove-Item Env:SEED_PASSWORD, Env:SEED_ADMIN_PASSWORD
```

رقم System Admin التجريبي هو `01000000000` وكلمة مروره هي قيمة `SEED_ADMIN_PASSWORD`. بقية حسابات الـSeed تستخدم `SEED_PASSWORD`. هذه ليست بيانات إنتاج.

## إنشاء System Admin وOwner

- في التطوير والاختبارات: الـSeed ينشئ System Admin واحدًا.
- بعد دخوله، ينشئ System Admin حساب Owner من `/system-admin` بكلمة مرور مؤقتة طولها 12 حرفًا على الأقل؛ يفرض النظام تغييرها عند أول دخول.
- في الإنتاج: بعد تطبيق الهجرات، مرّر `BOOTSTRAP_ADMIN_NAME` و`BOOTSTRAP_ADMIN_PHONE` و`BOOTSTRAP_ADMIN_EMAIL` الاختياري و`BOOTSTRAP_ADMIN_PASSWORD` مؤقتًا وفريدًا بطول 14–128 حرفًا ويحتوي حرفًا كبيرًا وصغيرًا ورقمًا ورمزًا، ثم شغّل `npm run admin:bootstrap` مرة واحدة؛ صورة أدوات Compose تحتوي الأمر. يتحقق السكربت من القيم ويرفض الـplaceholders والقيم المتوقعة، ويأخذ قفل PostgreSQL advisory، ويرفض إنشاء مسؤول ثانٍ ما دام يوجد System Admin غير محذوف، ويشفّر كلمة المرور، ويضبط `mustChangePwd=true`، ويسجل Audit داخل المعاملة نفسها. احذف متغيرات الـbootstrap فور النجاح ولا تمررها إلى تشغيل الويب الدائم، ولا تستخدم الـSeed في الإنتاج. توجد أمثلة Compose آمنة لإدخال السر في [دليل النشر](DEPLOYMENT.md).

## حد الفروع وطلب فرع

`BrandSettings.maxBranches` حد على مستوى البراند كله وقيمته الافتراضية 1. يرسل Owner الطلب من `/admin` دون إنشاء فرع مباشر. يراجعه System Admin في `/system-admin`. عند الموافقة تُجمع بيانات الفرع، ويُرفع الحد عند الحاجة، ويُنشأ الفرع وعضوية المالك وساعات العمل الافتراضية داخل معاملة Serializable واحدة.

بعد الإنشاء يجب تجهيز الفرع من `/admin/setup`: الموظفون، الفرق والأعضاء والقدرات والزونات، المناطق، الساعات وفترات الراحة والإجازات، مصفوفة الانتقال، وسائل الدفع، السعة ونمط التوزيع، وقوالب الـChecklist.

## الدفع والرصيد والاشتراكات

- يستطيع العميل اختيار استخدام رصيد التعويضات عند إنشاء الحجز. يخصم الخادم بحد أقصى إجمالي الحجز داخل معاملة واحدة، ويضيف حركة سالبة إلى `CustomerCreditTransaction`، ويسجل `Booking.creditAppliedAmount`، ويخفض التحويل المطلوب مقدمًا. إذا غطى الرصيد هذا المطلوب ينتقل الحجز إلى مراجعة التشغيل دون إثبات دفع، وعند مراجعة أي تحويل لاحق يحسب النظام النقد المعتمد مع الرصيد المستخدم دون تجاوز إجمالي الحجز.
- إذا انتهت مهلة الحجز المؤقت قبل رفع الإثبات، أو حررته الإدارة والحجز ما زال ينتظر الإثبات، يتحول الحجز إلى `EXPIRED` ويعود الرصيد المستخدم مرة واحدة وتتحرر زيارة الاشتراك المحجوزة. أما تحرير الـHold أثناء مراجعة الدفع أو التشغيل فيحرر السعة فقط ولا يمحو حقًا ماليًا أو حجز زيارة معلقًا.
- عند اعتماد إثبات الدفع يعيد الخادم أخذ قفل سعة الفرع وفحص الموعد المحفوظ قبل أي كتابة مالية، ثم ينشئ أو يمدد Hold صالحًا له. إذا ضاعت السعة تُرفض المعاملة بلا تحديثات دفع جزئية، ويحسب التحرير اليدوي بقاء الحجز من الـHolds الحية فعلًا بعد التحرير.
- يعرض معالج الحجز اسم سياسة الإلغاء الفعلية للخدمة وإصدارها ومهلة الإخطار ونصها العربي. يرسل التأكيد معرف السياسة ومراجعة دقيقة مشتقة من `updatedAt`؛ فإذا عدّلها المسؤول بعد عرضها يرفض الخادم التأكيد القديم ويطلب من العميل مراجعة القاعدة الجديدة قبل الحجز.
- تفصل تسوية الإلغاء بين الاسترداد النقدي، ورصيد العميل، والمبلغ المحتفظ به؛ لا تتداخل الأجزاء ويجب أن تساوي كامل المدفوع. لا يتجاوز الاسترداد النقدي ما دُفع نقدًا فعلًا، ويُعاد الرصيد المستخدم إلى دفتر الرصيد غير القابل للتعديل عندما تقضي سياسة القرار بذلك. وإذا رفض التشغيل حجزًا سبق دفعه أو استخدام رصيد فيه، ينشئ النظام تسوية إرجاع كاملة وCancellation/Refund قابلًا للمتابعة بدل ترك القيمة دون مسار.
- تحكم السياسة المقبولة نفسها الإلغاء وإعادة الجدولة، بما فيها طلب إلغاء يختار `RESCHEDULE` كحل مفضل؛ ويعيد المدير التحقق باستخدام وقت إنشاء الطلب الأصلي لا وقت المراجعة. وعند إعادة حجز نهائي للمراجعة يصبح Review-only: تُمنع الانتقالات وعمليات Refund/Hold، ويختفي من طوابير التشغيل، ويرى العميل حالته النهائية الأصلية بلا أزرار، ثم يغلق Owner المراجعة بإعادة الحالة الأصلية نفسها.
- يختار طلب الاشتراك فرعًا نشطًا مؤهلًا تلقائيًا من أحدث حجز مؤهل للعميل، ثم يستخدم أول فرع مؤهل بترتيب ثابت عند عدم وجوده. يثبت سعر الخطة ومدة الصلاحية وقت الطلب، ويبدأ `PENDING_PAYMENT`، ولا يعرض إلا وسائل الدفع النشطة لذلك الفرع. يرفع العميل إثبات JPG/PNG/WebP/PDF خاصًا، ويراجعه Operations Manager أو Owner أو System Admin مع سبب؛ ولا يصبح الاعتماد صالحًا إلا إذا ساوى المبلغ سعر الشراء المثبت تمامًا. التفعيل خطوة مستقلة محمية، ويحوّل النظام الاشتراك النشط المنتهي إلى `EXPIRED` عند أول قراءة لاحقة في صفحات العميل أو الإدارة أو التقارير مع تسجيل Audit.

## الاختبارات

شغّل قبل أي إصدار:

```bash
npm run typecheck
npm run lint
npm test
npm run test:e2e
npm run build
npm run audit
```

`npm run test:e2e:list` يعرض الحالات فقط ولا ينفذها. ما لم يشر `E2E_BASE_URL` إلى خادم خارجي قائم، يشغّل Playwright سيرفر التطوير ويديره على `E2E_PORT` (الافتراضي 3000، ويمكن استخدام 3417 كمنفذ محلي معزول). تغطي حالات القبول المرتبطة بقاعدة البيانات سيناريوهات الـMaster للحجز الكامل، وتنافس آخر سعة، وإعادة رفع إثبات الدفع، والاشتراكات، وحد الفروع، وعزل الصلاحيات، وخارج التغطية (1 و3 و6 و8 و9 و10 و12). تحتاج `E2E_DATABASE_URL` يشير إلى PostgreSQL منفصل ومهاجر ومعبأ بالـSeed، وتتخطى نفسها إذا لم يتوفر الشرط. لا توجّهها أبدًا إلى بيانات التطوير أو الإنتاج، وتخلّص من قاعدة E2E أو أعد بنائها بعد التشغيل. يفرض `npm run audit` سياسة الحزم عند مستوى High.

ينشئ `.github/workflows/ci.yml` قاعدتي PostgreSQL 16 منفصلتين: Job للتحقق من الهجرات وSchema drift وسياسة الحزم وTypeScript وLint وUnit والبناء، وJob يهاجر قاعدة E2E ويملؤها بالـSeed ويثبت Chromium ثم يشغّل Playwright كاملًا.

## Docker والنشر

بعد إنشاء `.env` بقيم إنتاج حقيقية:

```bash
docker compose build web migrate
docker compose up -d db
docker compose run --rm migrate
docker compose up -d web
docker compose ps
```

الخدمتان مربوطتان على `127.0.0.1`؛ استخدم Reverse Proxy مع TLS. البيانات في volume اسمه `postgres_data` والملفات في `uploads_data`، ويجب نسخ الاثنين احتياطيًا معًا.

## التخزين والأمان

- تُكتب ملفات الحجوزات عبر `StorageAdapter` قابل للاستبدال؛ يستخدم `STORAGE_DRIVER=local` مجلد `UPLOAD_DIR` الدائم، ويمكن تركيب Adapter آخر دون تغيير التفويض أو روابط قاعدة البيانات. ترتبط الملفات بسجل `BookingFile` وتُعرض من `/api/files/...` بعد فحص الصلاحية. تشترك إثباتات دفع الاشتراكات في التخزين الخاص وترتبط بـ`SubscriptionPaymentProof`؛ يقرأ العميل إثباته، ويقرأه مدير الاشتراك المصرح له في الفرع، ولـOwner وSystem Admin وصول إداري على مستوى البراند. لا تصبح صورة قبل/بعد الخدمة عامة إلا بعد موافقة العميل الصريحة على النشر ثم اعتماد Owner المسجل. تعيد واجهات المتصفح، ومنها إثبات الاشتراك، رسم JPG/PNG/WebP داخل canvas مع الحفاظ على الاتجاه المرئي، وتقليل الأبعاد/الجودة، وإزالة EXIF/GPS، ثم ترفع WebP؛ والمتصفح غير المدعوم يعيد الملف الأصلي. يظل الخادم يفرض تطابق الامتداد وMIME وmagic bytes وحد 10MB للأنواع JPG/PNG/WebP/PDF. أدلة قبل/بعد/أثناء/الضرر تقبل الصور فقط، ولا تُحتسب نحو حد الصور إلا سجلات image MIME؛ يبقى PDF متاحًا لأدلة الدفع والاسترداد والحالات والاشتراكات المستندية.
- صور الكتالوج التي تشير إليها خدمة نشطة تصبح عامة من `/api/catalog-media/...`؛ بقية صور المعاينة لا يراها إلا Owner أو System Admin.
- الجلسة JWT موقعة داخل Cookie من نوع HttpOnly، بينما تُحفظ بصمة SHA-256 وحالة الإلغاء في PostgreSQL. تغيير كلمة المرور أو الدور أو حالة الحساب يبطل الجلسات القائمة.
- الـrate limit وقفل محاولات الدخول محفوظان في PostgreSQL تحت بصمة HMAC للمعرّف، وتستخدم الزيادة قفلًا استشاريًا لتعمل بصورة متسقة بين نسخ التطبيق دون تخزين رقم الهاتف الخام في جدول التحكم.
- استعادة كلمة المرور Workflow يدوي من صفحة الدخول برد عام يمنع كشف وجود الحساب، مع rate limit للهاتف والـIP ومنع تكرار الطلب المعلق. يرى Operations Manager عملاء فروعه فقط، بينما يرى Owner/System Admin الطابور الكامل في `/operations/password-resets`. تتطلب المعالجة سبب تحقق وكلمة مؤقتة قوية، وتبطل الجلسات والقفل، وتجبر العميل على تغييرها، وتسجل Audit؛ ولا يرسل النظام Email أو SMS أو WhatsApp تلقائيًا.

## حدود مقصودة

النظام ليس SaaS ولا Multi-tenant. لا يوجد WhatsApp API (فقط رابط `wa.me` يدوي)، ولا SMS/Email آلي، ولا Payment Gateway، ولا Google Maps أو GPS حي، ولا Route Optimization خارجي، ولا CRM أو Ads أو Zapier/Make، ولا Inventory أو نظام محاسبة كامل أو Chatbot أو Marketplace.
